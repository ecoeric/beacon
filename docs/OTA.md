# Beacon OTA updates through SideStore

This document covers the one-tap iPhone update path: GitHub Actions builds Beacon, publishes an
unsigned IPA and a SideStore/AltStore source feed, and SideStore signs/installs the update on the
phone. It replaces the USB/AltServer step for routine updates.

> **Current blocker on this host:** the GitHub repository is not publicly readable from here
> (`https://api.github.com/repos/ecoeric/beacon` returns `404` without credentials), and this
> machine has no GitHub credentials or SSH key. The workflow and feed generator are implemented
> and locally validated, but the real macOS build, GitHub Release publication and a SideStore
> install have **not** been run. See [Limits](#limits-and-unverified-parts).

## 1. Audit: the old process

The existing `.github/workflows/ios-build.yml` did this:

1. On a push touching `ios/**`, start two `macos-26` jobs.
2. `unsigned-ipa`: select `/Applications/Xcode_26.2.app`, build Release for
   `generic/platform=iOS` with `CODE_SIGNING_ALLOWED=NO`, package `Payload/Beacon.app` as
   `Beacon-unsigned.ipa`, write a checksum/build-info, and upload a 30-day workflow artifact.
3. `simulator-tests`: build and run the XCTest suite on an iPhone simulator.
4. Stop. There was no GitHub Release, no source JSON, and no public URL.

The manual follow-up was:

```bash
scripts/install_ipa_linux.sh --ipa Beacon-unsigned.ipa   # USB + AltServer + Apple ID
```

That path is still useful as a fallback, but it requires a cable, a trusted device and a fresh
7-day development signature. The current signing method is **not** an Apple Developer certificate:
the IPA is unsigned and AltServer signs it with a free Apple ID. SideStore uses the same model:
it signs an unsigned IPA on-device with the user's existing certificate.

The existing IPA was already structurally suitable for SideStore:

* `Payload/Beacon.app/Beacon`, arm64, unsigned;
* bundle id `dev.ericserver.beacon`;
* bundled private CA and `MinimumOSVersion` 17.0;
* no provisioning profile or `_CodeSignature` directory.

What was missing was version progression, a public IPA URL, an icon URL and a source feed. The
workflow also had `permissions: contents: read`, no release step, no tags, and no source release.
The marketing version and build number were hardcoded to `1.0` / `1`, so even a manually hosted
feed would never have offered an update.

## 2. Architecture

```
Linux edit + git push
        │
        ▼
GitHub Actions (macos-26)
  ├─ unsigned arm64 IPA
  └─ simulator tests
        │  both must pass
        ▼
publish job (ubuntu-latest)
  ├─ verify IPA: bundle id, version/build, CA, unsigned
  ├─ create immutable release v1.0.<run_number>
  │    Beacon-unsigned.ipa + checksum + build-info + release notes
  ├─ merge apps.json history
  ├─ update fixed prerelease "beacon-source"
  │    apps.json + Beacon-AppIcon.png
  └─ fetch apps.json back and verify it
        │
        ▼
GitHub Release asset URLs (public)
        │
        ▼
SideStore → Sources → refresh → Updates → Update
        │
        ▼
SideStore downloads the unsigned IPA, signs it with the existing Apple ID certificate,
installs it over the same bundle id (app data preserved).
```

The source feed is a **fixed release tag** (`beacon-source`) whose `apps.json` asset is replaced
on every release. That gives SideStore a stable URL:

```
https://github.com/<owner>/<repo>/releases/download/beacon-source/apps.json
```

The IPA itself is attached to an immutable, versioned release:

```
https://github.com/<owner>/<repo>/releases/download/v1.0.<run>/Beacon-unsigned.ipa
```

`apps.json` is generated by `scripts/ota_source.py`. It keeps up to 25 previous versions, newest
first; SideStore requires the first compatible version to be the latest. It writes both the modern
`versions` array and the deprecated flat fields for older AltStore clients, and includes the IPA
`sha256` and `buildVersion` for stronger identification.

## 3. Versioning

The workflow sets:

* `CFBundleShortVersionString` = `1.0.<GITHUB_RUN_NUMBER>`
* `CFBundleVersion` = `<GITHUB_RUN_NUMBER>`

`Info.plist` now uses `$(MARKETING_VERSION)` and `$(CURRENT_PROJECT_VERSION)`; the workflow passes
the values to `xcodebuild`. The built app is checked before packaging, so a failed substitution
fails the run rather than publishing a duplicate version. SideStore compares the marketing version,
so every successful run is newer than the last. Each feed version also carries `buildVersion`, so
SideStore can distinguish builds even if a version is re-published. Failed builds never create a
release.

## 4. One-time setup

### Option A — make the existing repository public

Use this only if you are comfortable exposing the source, LAN host name and private CA certificate
(the certificate is a public key, not a secret). No extra repository or token is required.

1. GitHub → repository → **Settings → General → Danger Zone → Change visibility → Public**.
2. GitHub → **Settings → Actions → General → Workflow permissions** → **Read and write
   permissions** (or ensure the repository policy allows the job-level `contents: write`).
3. Push the workflow (the next section). The publish job checks visibility and fails with a clear
   error if the target is still private.
4. Copy the source URL from the workflow run summary.

### Option B — keep the source private, publish a public release mirror

Recommended if the repository contains private infrastructure details.

1. Create an empty **public** repository, for example `ecoeric/beacon-releases`, with a README.
   It only receives IPA/feed assets; no source is pushed there.
2. Create a **fine-grained personal access token** limited to that repository with
   **Contents: Read and write** (no other permissions).
3. In the private `beacon` repository, add:

   ```bash
   gh variable set BEACON_RELEASE_REPO --body "ecoeric/beacon-releases" --repo ecoeric/beacon
   gh secret set BEACON_RELEASE_TOKEN --repo ecoeric/beacon   # paste the fine-grained PAT
   ```

4. Ensure the private repository's Actions policy allows `contents: write` for the publish job.
5. Push the workflow. The build stays in the private repository; the IPA, icon and `apps.json`
   are uploaded to the public mirror using the PAT. The publish job refuses a private target.

No Apple ID, certificate, provisioning profile or backend token belongs in GitHub. SideStore signs
the unsigned IPA on the phone.

## 5. Normal future updates

```bash
cd ~/beacon
# edit Swift/backend/docs...
git add -A
git commit -m "Describe the change"
git push origin master
```

Then:

1. Wait for the **iOS build, tests & SideStore release** workflow to finish green.
2. Open **SideStore → Sources**, pull to refresh if needed.
3. Open **Updates** (or the Beacon app page) and tap **Update**.
4. SideStore downloads the new IPA, signs it with the existing certificate and installs it over
   `dev.ericserver.beacon`. App data and the Keychain token stay intact.

There is no USB step, no AltServer step and no Windows dependency. A backend-only change does not
trigger the iOS workflow; use **Actions → iOS build… → Run workflow** if you want a new build
anyway.

To force a build without changing iOS code:

```bash
gh workflow run ios-build.yml --repo ecoeric/beacon --ref master
```

## 6. Source URL and SideStore setup

After the first successful publish, the run summary prints:

```
SideStore source URL:
https://github.com/<owner>/<repo>/releases/download/beacon-source/apps.json
```

Add it once:

1. Install and set up SideStore normally (it needs a one-time computer-assisted install and a
   working LocalDevVPN).
2. SideStore → **Sources** → **+** → paste the source URL.
3. Open the source, tap **Beacon**, then **Install**. SideStore signs it with your Apple ID.
4. Future versions appear under **Updates**. Tap **Update**.

### One-time migration from the AltServer/USB install

SideStore and AltServer are different signers. If the copy currently on the phone was installed by
`scripts/install_ipa_linux.sh`, iOS may refuse an in-place update from SideStore because the signing
certificate/profile does not match. That is a one-time migration, not a per-update problem:

1. Add the source and install Beacon **from SideStore** once.
2. If iOS reports a signing/provisioning error over the old copy, delete the old Beacon app and
   install the SideStore copy. Re-enter the server URL/token in Beacon if the data is not preserved
   (the Keychain item often survives, but do not rely on it).
3. Every later version is signed by the same SideStore certificate, so **Updates → Update**
   preserves app data and needs no USB.

A direct add link is:

```
sidestore://source?url=https://github.com/<owner>/<repo>/releases/download/beacon-source/apps.json
```

### Free Apple ID limits

A free Apple ID used by SideStore is limited to 3 active apps (including SideStore) and 10 new app
IDs per week. Beacon uses one slot. The 7-day development signature still needs SideStore's
background refresh/VPN; OTA updates do not remove that requirement.

## 7. Failure handling

* The publish job has `needs: [unsigned-ipa, simulator-tests]`; a failed build **or** failed
  simulator test means no release and no feed change.
* Versioned releases are never overwritten or deleted. Re-running the same run number only
  replaces assets in that same release; a new commit gets a new run number and a new version.
* The source feed is updated only after the IPA release is created and the IPA is verified.
* If the source-feed upload fails after the IPA release exists, the old feed still points to the
  last working IPA. The orphaned release can be cleaned up manually; it is harmless.
* The publish job refuses private targets, because SideStore could not download them.
* Push-triggered runs are not cancelled by a newer push (`cancel-in-progress` is false); PR runs
  may be cancelled.
* GitHub's release-asset CDN can serve a cached `apps.json` for a few minutes. Pull to refresh in
  SideStore if the new version is not immediately visible.

## 8. Security

* The IPA is **unsigned** and contains no Apple credentials, provisioning profile, backend token
  or password. It contains the app, its public CA certificate and the default LAN URL.
* SideStore signs with the user's Apple ID on-device; no signing secret is stored in GitHub.
* The optional mirror PAT is a fine-grained secret with only `Contents: Read and write` on the
  public release repository.
* The bundle identifier remains `dev.ericserver.beacon`; updates preserve app data.
* Backend credentials stay in the app's Keychain and are entered by the user; they are not built
  into the IPA.
* The source feed exposes only the IPA, icon and release notes.

## 9. Local validation

```bash
./scripts/validate_ota.sh
```

This runs the source-generator unit tests, checks the committed icon is reproducible, verifies the
Info.plist version placeholders and checks the workflow structure. If `actionlint` is installed it
also lints expressions and shell blocks. The generator was additionally run against the existing
real `artifacts/Beacon-unsigned.ipa` (version 1.0, build 1) and accepted its unsigned arm64 layout,
bundle id, CA and Info.plist.

## 10. Limits and unverified parts

These are real limitations, not assumptions:

* **No end-to-end run on this host.** There is no GitHub authentication and no macOS/Xcode here.
  The workflow cannot be pushed, dispatched or observed; no GitHub Release or public feed exists
  yet.
* **No iPhone is attached**, so SideStore installation/update was not exercised. The feed and IPA
  are structurally valid and the existing IPA passed the generator's checks, but only a real
  SideStore update proves the final step.
* The repository is currently private/404 without credentials. Choose Option A or B before
  expecting SideStore to fetch anything.
* The app icon is new and was generated and validated as a 1024x1024 PNG, but its appearance in a
  real Xcode build has not been visually verified.
* SideStore still requires its one-time setup, LocalDevVPN and periodic 7-day refresh. "One tap"
  means one tap on **Update**, not unattended installation.
* The source feed uses a fixed GitHub Release asset URL; CDN caching can delay a new version by a
  few minutes.
