it was tested, and what it does not do. It is updated as features are completed; every claim
below corresponds to code in this repository and to a test that was executed.

| Status | Meaning |

| **Planned** | Designed, not built. |
| **Unavailable** | Deliberately not provided because the platform/environment cannot support it. |

## 2.1 HTTPS API service under systemd

* **Behaviour**: FastAPI app served by Uvicorn on `192.168.1.83:8091` with TLS, JSON errors,
  security headers and a 20 s shutdown path. Restarts automatically; data survives restarts.
* **Files**: `backend/beacon/main.py`, `backend/beacon/asgi.py`, `deploy/beacon-api.service`,
  `deploy/beacon.env`, `scripts/install.sh`.
* **Configuration**: `BEACON_BIND`, `BEACON_PORT`, `BEACON_DATA_DIR`, `BEACON_TLS_CERT/KEY`;
  full list in `deploy/beacon.env`.
* **Internals**: `create_app()` mounts four routers under `/api/v1`, registers exception
  handlers for the five service error types (`{"error","message","detail"}`), starts the metrics
  sampler and hourly retention loop in `lifespan`, and runs one retention sweep at boot.
* **Test**: `systemctl is-active beacon-api`; `beacon doctor`; `pytest backend/tests`.
* **Limitations**: single process (no multi-worker) — SQLite + in-memory rate limiting assume one
  instance; restart takes ~1 s.
* **Debug**: `sudo journalctl -u beacon-api -n 100 --no-pager`, `beacon service logs`.

## 2.2 Private CA + SPKI pinning

* **Behaviour**: `beacon tls init` generates an ECDSA P-256 root CA (10 years) and a leaf for
  `192.168.1.83`, `127.0.0.1`, `ericserver`, `localhost` (397 days, under Apple's 398-day limit).
  The app validates the chain against the CA bundled at `ios/Beacon/Resources/ca.crt`
  (`SecTrustSetAnchorCertificates`, anchor-only) and, when configured, requires the leaf
  SPKI SHA-256 pin to match.
* **Files**: `backend/beacon/tls.py`, `ios/Beacon/Networking/PinnedSession.swift`,
  `ios/Beacon/Networking/ServerConfiguration.swift`, `scripts/install.sh` (copies the CA into the
  app bundle), `docs/SETUP.md`.
* **Endpoints**: none (transport-level).
* **Test**: `tests/test_persistence_tls.py` builds a real Uvicorn HTTPS server and performs an
  authenticated request with the generated CA, then asserts the same certificate is rejected by
  the default trust store; `beacon tls show` prints SANs and pin; live smoke test performs an
  HTTPS request with the CA.
* **Limitations**: certificate rotation (`beacon tls init --force`) requires re-bundling
  `ca.crt`; the app fails closed if the bundle is missing.
* **Debug**: `openssl s_client -connect 192.168.1.83:8091 -CAfile data/tls/ca.crt`.

## 2.3 Scoped bearer tokens

* **Behaviour**: opaque 256-bit tokens; only SHA-256 digests stored. Scopes: `read`, `action`,
  `admin` (hierarchy) and `agent` (runtime-only). UI tokens cannot pull the queue; runtime
  endpoints require the `agent` token. Revocation is immediate.
* **Files**: `backend/beacon/security.py`, `backend/beacon/deps.py`, `backend/beacon/cli.py`.
* **Endpoints**: authentication applies to every route except `/health`; identity at `/whoami`.
* **Data**: `token` table + `data/secrets/<role>.token` (0600). Roles created by `beacon init`:
  `ios` (read,action,admin), `agent` (agent,read), `cli` (read,action,admin).
* **Test**: `tests/test_auth.py` (8 tests), including 401/403/428 and the agent-only restriction;
  live smoke test checks unauthenticated rejection and queue isolation.
* **Debug**: `beacon token list`, `beacon token revoke <name>`, `/api/v1/audit`.

## 2.4 Agent binding to the Cherry Studio runtime

* **Behaviour**: read-only evidence from three sources — SQLite
  (`~/.config/CherryStudio/Data/cherrystudio.sqlite`, opened `mode=ro`), transcript mtime, and
  `/proc` mapping of the per-session DSH runtime (composition filename contains the session id).
  `BEACON_AGENT_ID` restricts detection to this agent's sessions.
* **Files**: `backend/beacon/services/agent_runtime.py`.
* **Data**: no writes to Cherry Studio. Session id, last activity, pending assistant turn,
  runtime pid and uid.
* **Test**: `tests/test_agent_status.py` (uses a synthetic database with the real schema),
  `tests/test_interrupt.py` (runtime resolution against a controlled process); live
  `beacon doctor` shows the resolved pid.
* **Limitations**: if Cherry Studio is closed, evidence degrades to the last snapshot and the
  state becomes `disconnected`/`unknown`; no support for other agent runtimes.
* **Debug**: `beacon agent status` prints the evidence list with ages.

## 2.5 Agent state derivation with evidence

* **Behaviour**: derives one of nine states, first match wins: `disconnected`, `failed`,
  `interrupted`, `working`, `waiting_for_messages`, `waiting_for_input`, `completed`, `idle`,
  `unknown`. Returns the evidence used and `data_age_seconds`.
* **Files**: `backend/beacon/services/agent_status.py`, `backend/beacon/schemas.py`.
* **Endpoint**: `GET /api/v1/agent/status`.
* **Test**: matrix tests in `tests/test_agent_status.py` (pending turn → working, queue →
  waiting_for_messages, awaiting input, error turn, stale/no runtime → disconnected/unknown).
* **Limitations**: heuristics are evidence-based, not a control protocol; a runtime that is alive
  but silent for >15 min is reported `idle` with a note.
* **Debug**: the `evidence[]` array in the payload is the ground truth used.

## 2.6 Status action (read-only, 1–3 sentences)

* **Behaviour**: `GET /api/v1/agent/status/summary` returns a deterministic summary composed by
  `render_status_summary()` — a pure function over the status payload. No HTTP client, no LLM, no
  queue writes, no conversation writes. Enforced to 1–3 sentences.
* **Files**: `backend/beacon/services/status_summary.py`,
  `backend/beacon/routers/agent.py`, `ios/Beacon/Features/Agent/AgentView.swift` (`StatusSheet`).
* **Test**: unit tests for every state (`tests/test_agent_status.py::test_status_summary_*`),
  the Python sentence-count assertion, the Swift fixture test, and the live smoke test which
  compares two calls, checks 1–3 sentences, and asserts the snapshot/queue/turn did not change.
* **Debug**: the response includes `based_on` (evidence sources) and `deterministic: true`.

## 2.7 Message queue (suggestion / continue / cancel)

* **Behaviour**: durable queue with monotonic `seq`; states `pending → delivered → acknowledged →
  processed` (terminal) and `pending → cancelled`. Sending is idempotent via client-provided key.
  Continue requires no text; optional note is appended.
* **Files**: `backend/beacon/services/message_queue.py`, `backend/beacon/routers/agent.py`,
  `ios/Beacon/Features/Agent/AgentView.swift`.
* **Endpoints**: `POST /agent/messages`, `POST /agent/continue`, `DELETE /agent/messages/{id}`,
  `GET /agent/messages`, `GET /agent/queue`.
* **Data**: `agent_message` table; `data/agent/inbox.jsonl`.
* **Test**: `tests/test_queue.py` (12 tests: ordering, transitions, idempotency, cancel rules,
  immutability after delivery, agent-scope requirement). Live smoke test queues, delivers,
  acknowledges, processes and cancels a message.
* **Limitations**: delivery is cooperative (the agent must call the checkpoint endpoint at a safe
  point); there is no push channel for message delivery.
* **Debug**: `beacon queue list`, `beacon agent checkpoint` (agent token).

## 2.8 Checkpoint delivery protocol + inbox mirror

* **Behaviour**: `POST /api/v1/agent/checkpoint` atomically marks pending messages delivered,
  increments `attempts`, returns them (max 25), mirrors them to `data/agent/inbox.jsonl`, writes
  an audit row and a `agent_message_delivered` activity item. Pending checkpoint interrupts are
  returned in the same response.
* **Files**: `backend/beacon/services/message_queue.py`, `backend/beacon/routers/agent.py`,
  `backend/beacon/cli.py` (`beacon agent checkpoint`).
* **Test**: `tests/test_queue.py` (ordering + inbox mirror + no re-delivery), live smoke test.
* **Limitations**: the agent must be instructed (workspace instructions) to call it at turn
  boundaries; stale pending messages are not auto-expired.
* **Debug**: `stat data/agent/inbox.jsonl`, `SELECT * FROM agent_message ORDER BY seq`.

## 2.9 Direct interrupt + cooperative interrupt

* **Behaviour**: `POST /api/v1/agent/interrupt` (`X-Beacon-Confirm: agent-interrupt`, admin only,
  1/15 s). `mode=signal` resolves the session's runtime pid, verifies uid and cmdline, sends
  `SIGINT`, waits up to 5 s for the process to exit (zombies count as exited) and records pid,
  signal, exit observation and evidence. `mode=checkpoint` records a request returned to the agent
  at its next checkpoint. Both bypass the queue; neither writes to the conversation.
* **Files**: `backend/beacon/services/interrupts.py`, `backend/beacon/routers/agent.py`,
  `ios/Beacon/Features/Agent/AgentView.swift` (`InterruptSheet`).
* **Data**: `interrupt` table; audit rows `agent.interrupt.request`, `.signal`,
  `.acknowledge`; activity item `agent_interrupted`.
* **Test**: `tests/test_interrupt.py` — spawns a controlled process whose argv matches a fake
  runtime, asserts SIGINT delivery, exit observation, evidence and audit; 409 when no runtime;
  428 without confirmation; 429 rate limit; checkpoint mode delivery + acknowledgement.
  **The live agent runtime was never signalled during development** (it hosts this work).
* **Limitations**: `signal` ends the runtime process — Cherry Studio reports the turn as
  interrupted and the session journal is preserved; there is no attempt to "pause" a single tool.
* **Debug**: `beacon agent interrupts`, `GET /agent/interrupts`, `journalctl -u beacon-api`.

## 2.10 Agent status snapshot publishing

* **Behaviour**: `PUT /api/v1/agent/status` (agent token) upserts project, stage, activity, last
  milestone, next action, blockers, `awaiting_input`, state override and progress; emits activity
  items for "waiting for input" and "completed".
* **Files**: `backend/beacon/routers/agent.py`, `backend/beacon/services/agent_status.py`,
  `backend/beacon/cli.py` (`beacon agent status-set`).
* **Test**: `tests/test_agent_status.py`, live use by the AI agent driving this project
  (`beacon agent status-set …`), which is what the dashboard currently displays.
* **Limitations**: last write wins per agent id; no history table (current snapshot only).

## 2.11 Milestones

* **Behaviour**: ordered milestone records with title, summary, change list, phase, timestamp and
  up to four screenshots. Creating one emits a `milestone_completed` activity item.
* **Files**: `backend/beacon/services/milestones.py`, `backend/beacon/routers/milestones.py`,
  `ios/Beacon/Features/Milestones/MilestonesView.swift`.
* **Endpoints**: `GET /milestones`, `GET /milestones/{id}`, `POST /milestones`,
  `POST /milestones/{id}/screenshots`.
* **Test**: `tests/test_milestones.py`; live milestone #1 with four screenshots.
* **Limitations**: no editing/deletion endpoint (history is append-only by design).

## 2.12 Screenshot capture (four real sources)

* **Behaviour**: server-side capture of real artifacts, never synthesized:
  `text` runs one of 10 allow-listed read-only `beacon` commands and renders its real output;
  `api` renders an allow-listed local API JSON response; `window` grabs the X11 display with
  `ffmpeg -f x11grab`; `file` ingests a real image produced elsewhere (e.g. Xcode simulator) from
  the project artifacts directories.
* **Files**: `backend/beacon/services/capture.py`, `backend/beacon/routers/milestones.py`,
  `backend/beacon/cli.py` (`beacon screenshot capture`).
* **Test**: `tests/test_milestones.py` (text capture end-to-end, allow-list rejection, preview),
  live smoke test (doctor capture), and live window capture of the Cherry Studio agent UI used in
  milestone #1.
* **Limitations**: `window` captures the whole 1366×768 display (no per-window API), requires an
  X session; `file` cannot read arbitrary paths.
* **Debug**: `ls data/captures`, capture JSON sidecars include source/title/caption.

## 2.13 Screenshot storage and retrieval

* **Behaviour**: images stored at `data/screenshots/<milestone>/<epoch>-<id8>-<name>.png`, with
  SHA-256, dimensions, caption, source, timestamps and expiry. Served as `FileResponse` with
  `Cache-Control: private`; expired or deleted images answer 410/404.
* **Files**: `backend/beacon/services/screenshots.py`, `backend/beacon/routers/milestones.py`,
  `ios/Beacon/Design/Components.swift` (`AsyncScreenshot`), `ios/.../ScreenshotViewer.swift`.
* **Test**: `tests/test_milestones.py` (upload, fetch, dimension parsing, expiry 410, path escape
  → 500), `tests/test_persistence_tls.py` (durability), live fetch via API.
* **Limitations**: no thumbnails generated (full image is served; the app downsizes for the grid).

## 2.14 7-day retention with read guard

* **Behaviour**: `expires_at = created_at + 7 days` (`BEACON_SCREENSHOT_RETENTION_DAYS`). Three
  layers: read guard (410 once expired), daily timer (`beacon-retention.timer` at 03:41 with
  `Persistent=true`), and an hourly in-process sweep. The sweep deletes only files referenced by
  the `screenshot` table inside `data/screenshots`, prunes generated orphans older than 24 h,
  removes capture staging older than 48 h, keeps row metadata (history survives) and writes an
  audit row. Unexpected files are reported, never deleted.
* **Files**: `backend/beacon/services/retention.py`, `deploy/beacon-retention.*`,
  `backend/beacon/cli.py` (`beacon retention run --local`), `backend/beacon/main.py`.
* **Test**: `tests/test_milestones.py` — expiry sweep deletes file but keeps milestone text;
  unrelated files untouched; generated orphans removed; dry run; project-escape protection.
  **Live drill** (milestone #2, kept as a record): a real screenshot's `expires_at` was moved into
  the past, `sudo systemctl start beacon-retention.service` ran the shipped unit, the file was
  deleted, the API answered `410 expired`, the milestone summary stayed readable with
  `expired_screenshots: 1`, and the sweep wrote its audit row
  (`{"deleted_screenshots":1,"deleted_files":1,"kept":4}`).
* **Limitations**: retention is age-based only (no manual pinning); screenshots are not backed up
  beyond the regular `beacon backup`.
* **Debug**: `beacon retention status`, `systemctl list-timers beacon-retention.timer`,
  `data/screenshots` tree.

## 2.19 Minecraft monitoring

* **Behaviour**: server-list ping (version, protocol, MOTD, players + sample), mod loader/version
  and installed mod count detected from `libraries/net/neoforged/*` and `mods/*.jar`, process
  metrics (`/proc` pid, CPU %, RSS, uptime), recent log errors/events/tick warnings, backup

* **Files**: `backend/beacon/services/minecraft.py`,
  `backend/beacon/routers/monitoring.py`, `ios/Beacon/Features/Server/ServerView.swift`.
* **Test**: `tests/test_monitoring.py` (stopped server path, control confirmation), live smoke

  reported `NeoForge 21.1.252 · 91 mods`.
* **Limitations**: tick metrics unavailable; player list is the ping sample plus log join/leave
  reconstruction; no RCON/query enabled.

## 2.20 Minecraft controls with safeguards

* **Behaviour**: admin + `X-Beacon-Confirm: minecraft-<action>` + rate limit + player-online guard
  (`force` required) + audit. Start/stop/restart use, in priority order: supervised pty console
  (Beacon started the instance), RCON (if enabled with password), or SIGINT only when the
  installed server jar contains the `Server Shutdown Thread` hook (verified on disk). The server is
  never force-killed; a failed stop is reported, not escalated.
* **Files**: `backend/beacon/services/minecraft.py` (`Supervisor`, `start`, `stop`, `restart`,
  `rcon_command`), `backend/beacon/routers/monitoring.py`.
* **Test**: `tests/test_monitoring.py` (confirmation required, structured `no_launch_script`
  error, `not_running` on stop), graceful-hook detection verified live against the installed jars.
* **Limitations / honesty**:
  * The **live instance** was started manually in a terminal and has players; it was intentionally
    **not** stopped or restarted during development. Stop/restart against it were therefore not
    executed end-to-end; the code path is covered by unit tests and the hook detection was
    verified on the actual jars.
  * `start` refuses if any Minecraft process already runs for this folder; it also refuses to run
    a second instance if a previous stop did not complete.
  * Full console control requires the instance to be started by Beacon (pty) or RCON to be enabled
    (`enable-rcon=true` + password file), which needs one restart chosen by the operator.

## 2.21 Activity feed / in-app notifications

* **Behaviour**: deduplicated activity items for milestone completion, agent waiting/completed/

## 2.22 Audit trail

* **Behaviour**: every privileged action (interrupt, service control, Pi-hole toggle, milestone
  creation, screenshot capture/delete, retention, queue delivery, token identity) is recorded with
  timestamp, actor, target, detail and IP. `GET /audit` is admin-only.
* **Files**: `backend/beacon/security.py` (`audit`), routers.
* **Test**: `tests/test_interrupt.py` (interrupt audit), `tests/test_milestones.py`
  (screenshot delete), live `beacon api-get /api/v1/audit`.
* **Limitations**: no retention policy for audit rows yet (small volume).

## 2.24 iOS networking, pinning, Keychain

* **Behaviour**: `APIClient` (async/await, typed errors incl. offline/trust/confirmation),
  `PinnedSessionFactory` (private CA anchor + optional SPKI pin), `KeychainStore` (token + pin,
  device-only), `AppSettings` (server URL + secrets), `AppModel` (single source of truth, 15 s
  polling tied to scene phase, background-safe).
* **Files**: `ios/Beacon/Networking/*`, `ios/Beacon/App/AppModel.swift`.
* **Test**: 13 Swift tests on Linux (`cd ios && swift test`) covering decoding of live fixtures,
  formatting, configuration and the queue contract; the networking client is compiled by the
  Linux toolchain. iOS Keychain/pinning code is compile-covered only by Xcode.
* **Limitations**: no certificate pin rotation UI; pin is optional (CA anchor remains mandatory).

## 5. Known limitations and deliberate exclusions

1. **iOS build/run on this host**: no macOS/Xcode → the app cannot be compiled or launched here.
   All non-UI Swift code is compiled and tested; all Swift files are parsed; the Xcode project is
   structurally validated. Building and simulator screenshots are macOS steps (§`docs/SETUP.md`).
2. **iPhone installation/signing/distribution**: explicitly out of scope for this project.
3. **Push notifications (APNs)**: not implemented; the activity feed is in-app. `payload` and
   `kind` fields are the extension point.
4. **Live interrupt of the real agent runtime**: not executed (it hosts this work). Signal-mode
   behaviour is covered by tests against a controlled process with a matching argv.
5. **Live Minecraft stop/restart of the running instance**: not executed (players online, manual
   start). Detection of the graceful shutdown hook was verified on the installed jars.
6. **TPS/MSPT**: unavailable on this server (no spark, RCON/query disabled). The API says so
   instead of inventing numbers.
7. **Historical charts**: intentionally omitted; only current values are shown.
8. **Multi-agent support**: one agent/session binding at a time (`BEACON_AGENT_ID`).
9. **Docker write operations**: none, by design (read-only wrapper).
10. **Audit retention compaction**: not implemented (low volume).

## 6. Debugging playbook

| Symptom | Check |
|---|---|
| App cannot connect | `beacon doctor`; `openssl s_client -connect 192.168.1.83:8091 -CAfile data/tls/ca.crt`; verify `ios.token` and the CA bundled in the app |
| Agent shows stale/disconnected | `beacon agent status` (evidence list); is Cherry Studio running? `ps aux \| grep dsh-bridge` |
| Message never delivered | `beacon queue list`; is the agent calling `beacon agent checkpoint`? check `data/agent/inbox.jsonl` |
| Interrupt returns 409 | runtime not resolvable → use `mode=checkpoint`, or start the agent session |
| Pi-hole shows unreachable | `docker ps`; `curl http://192.168.1.83:8080/api/auth`; `data/secrets/pihole.password` |
| Minecraft shows stopped while running | ping blocked? `ss -tlnp \| grep 25565`; log path `~/Desktop/NeoForgeServer/logs/latest.log` |
| Docker metrics missing | `sudo -n /usr/local/lib/beacon/docker-read ps`; sudoers drop-in present? |
| Screenshot 410 | retention window passed (7 days) — expected; milestone text remains |
| Retention timer | `systemctl list-timers beacon-retention.timer`; `journalctl -u beacon-retention` |
